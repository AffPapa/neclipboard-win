## Границы данных

- История: не более 1000 записей, суммарно 15 MiB UTF-8 payload.
- Текст: до 500000 UTF-16 code units; список файлов до 100 путей, каждый до 32767 символов, общий текст до 500000. Файлы не открываются и не включаются в backup — сохраняются только пути.
- PNG: до 3 MiB декодированного файла и 8 млн пикселей; неподдерживаемые или недекодируемые данные отклоняются. Результат проверки immutable image payload разделяется между снимками, повторная запись не декодирует то же изображение заново.
- Настройки: 10–1000 элементов истории; до 100 исключений по именам процессов, до 1000 сниппетов, суммарно 2 MiB UTF-8 заголовков/содержимого сниппетов. Один заголовок до 200 символов, содержимое до 500000.
- Hotkey: ALT/CTRL/SHIFT, обязательны ALT или CTRL; A–Z, 0–9, F1–F11. F12 исключена как зарезервированная Windows. Пауза хранится nullable UTC.
- Внешний файл: не более 100 MiB для history/backup, 16 MiB для settings; это отдельная граница зашифрованного/JSON представления, учитывающая escaping, а не разрешение 100 MiB пользовательского payload.
- JSON: глубина 16, не более 50000 токенов; длины свойств и декодированных строк проверяются `Utf8JsonReader` до десериализации, включая `\uXXXX` escapes. Коллекции и суммарные payload проверяются затем. Все ограничения применяются и при записи.

Идентификаторы элементов/сниппетов должны быть непустыми и уникальными внутри коллекции; enum и UTC timestamps валидируются. Неверные обычные current/previous документы изолируются в `.corrupt-*`, данные не выводятся в диагностику. DPAPI CurrentUser остаётся механизмом защиты на диске; он не защищает от кода, уже работающего с правами того же Windows-пользователя.

## Формат и миграция

Новые ordinary documents имеют `Format`, `SchemaVersion: 1`, `Settings` или `Entries`. Старые зашифрованные raw `AppSettings` и массив истории 0.1.5 читаются; plaintext legacy settings после успешной зашифрованной записи удаляются. Изменённые данные сохраняются в envelope при следующем обычном сохранении. Неподдерживаемая будущая схема не принимается за текущую.

Проверка upgrade: синтетические старые encrypted документы → load с сохранением snippets/pins/настроек → save нового envelope → повторный load. PASS. Старый EXE 0.1.5 не читает новый ordinary envelope: для возврата нужно заранее сделанное совместимое backup либо сохранённые старые файлы; простая замена EXE назад не является поддерживаемым откатом. Формат backup остаётся `NeClipboardWin.Backup`, schema 1.

## Семантика restore

`SettingsService.TryRestoreWithHistory(historyStore, settings, entries)` возвращает `Applied`, `Failed` либо `RecoveryRequired`.

1. Полностью проверить и зашифровать новые документы.
2. Сохранить исходные `settings.dat`, `history.dat` и обе `.prev.dat` в уникальном `.restore-{id}`. Содержимое остаётся DPAPI ciphertext. Flush каждого файла и SHA-256 позволяют проверить полноту rollback-копии.
3. Атомарно записать небольшой `restore.pending.json`: версия, идентификатор транзакции, существование/длина/hash фиксированных файлов. Clipboard-содержимого в журнале нет.
4. Заменить настройки и историю, прочитать/проверить итог.
5. Удалить pending journal — точка commit. Убрать rollback-копии.

Любой ожидаемый отказ до commit запускает rollback. `Failed` означает, что исходные файлы восстановлены и проверены byte-for-byte; `RecoveryRequired` означает, что откат пока не удалось закончить. Пока существует неустранимый pending journal, новые save/clear/restore блокируются. Перед загрузкой на следующем запуске выполняется `RecoverPendingRestore`. Прерывание процесса до commit возвращает старую пару; после commit новая пара остаётся. Это согласованность через журнал, а не заявление об одной атомарной файловой операции на два документа.

Внутри процесса сервисы используют общий lock на каталог. UI дополнительно сериализует save/clear/restore/exit через gate, делает snapshots в правильном порядке и не пропускает старую отложенную запись через clear/restore (интеграция root). Одновременные независимые процессы предотвращает single-instance приложения.

## Проверки и фактические измерения

Исходные 13 verification groups прошли до изменений; save/load синтетических 150×100 KiB текстов занял 1385 ms в одном запуске. Новый test `invalid model rejection` затем падал на сохранении enum 99 — дефект был воспроизведён.

После изменений 30 verification groups PASS, сборка .NET 10 с `-warnaserror` — 0 ошибок/предупреждений. Среди новых проверок:

- invalid encrypted null/enum/future-schema/settings, реальные превышения count и aggregate bytes;
- ранний отказ oversized file, глубина/число JSON-токенов/escaped strings;
- plaintext и encrypted legacy migration;
- malformed Base64/PNG и pixel limit;
- отказ перед atomic replacement и реальная Windows sharing violation;
- verified rollback после первой замены, отказ во время rollback, запрещённые новые writes, успешный retry;
- четыре отдельные аварийно завершаемые child-process fixtures: после журнала, после settings, после history, перед commit;
- malformed recovery journal сохраняет исходные файлы и блокирует новые writes;
- deep snapshots, cached/truncated preview без разрыва surrogate pair, full-content search, Win32 INPUT layout regression.
- in-memory STA проверки Windows privacy markers: null, opt-out, malformed/bounded/disposed streams, DWORD endianness, неизменный payload и одновременные replay opt-out для history/cloud. Первоначально test обнаружил `ObjectDisposedException`; helper другого агента был исправлен, повторный прогон PASS.

Команда: `dotnet run --project tests/NeClipboardWin.Verification/NeClipboardWin.Verification.csproj -c Release` (SDK 10 из `global.json`). Все временные fixture-каталоги удаляются после проверки. `StorageSafety.FaultInjection` — internal-only deterministic test seam, не пользовательская настройка.

Модельный benchmark: один ПК, Release, .NET 10, без debugger; 150 записей, 14701650 символов, warm preview pass, затем 30 итераций. Каждая итерация запрашивает preview и делает два поиска по всем элементам: совпадение в конце содержимого и отсутствующий запрос. p50 — 15-я отсортированная выборка, p95 — 29-я.

| Реализация | p50 | p95 | Аллокации текущего потока за 30 итераций |
| --- | --- | --- | --- |
| Исходный `Models.cs`, тот же .NET 10 | 22.52 ms | 72.78 ms | 2552149856 B |
| Кэшированный preview + полный поиск | 4.38 ms | 4.91 ms | 1776 B |

Новый benchmark доступен через `--benchmark-models`; baseline harness с неизменённым исходным Models сохранён в ignored `artifacts/model-baseline-net10`. Это измерение моделей, не задержки настоящего окна или клавиатурного ввода. Нормализованный display стал короче по назначению; полный исходный текст, включая tail-совпадение, по-прежнему ищется. Исходный дополнительный замер на .NET 8 (26.85/81.81 ms) не используется для сравнения разных реализаций.

Новые единичные storage save/load запуски занимали от 167 до 1694 ms: большой разброс не позволяет приписывать изменение скорости storage конкретной оптимизации. Ускорение в этой работе доказано для preview/search, а не для диска.

## Native fixture handoff

Создан отдельный `tests/NeClipboardWin.DesktopVerification`: visible Windows Forms fixture, RAM-only сохранение поддерживаемого исходного clipboard, отказ при неизвестных форматах/изменении sequence, синтетические text/image/files, реальное поле-получатель, проверка точного результата, безопасный возврат буфера, кнопка конфликта hotkey. Воспроизведение проверяется только после явной очистки собственного синтетического буфера: первоначальная публикация fixture не может выдать ложный PASS за replay приложения. Fixture не посылает клавиши в другие окна. Сценарий находится в его README.

`App --qa-desktop <TEMP/NeClipboardWin-QA-*>` использует только временное хранилище. MainWindow разрешает реальные системные интеграции с fixture-only source/paste targets и synthetic marker; автозапуск в реестре отключён. Fixture собран self-contained, native тесты выполняет root через desktop automation. Наличие кода fixture здесь не считается успешным native E2E.

## Ограничения этих доказательств

Это не проверка физической потери питания, неисправного диска или съёмного носителя. Disk-full моделируется `IOException` перед replacement; реальный отказ проверен sharing violation. Реальный UI/clipboard/темы, долгие idle/leak-прогоны, скачанный EXE и GitHub pipeline покрываются другими этапами. DPAPI portability между Windows-аккаунтами не обещается. Проверку подписи и публикацию этот агент не выполнял.
